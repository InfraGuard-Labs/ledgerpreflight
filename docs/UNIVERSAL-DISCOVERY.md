# Universal discovery boundaries

Artifact discovery and compatibility analysis are separate phases. Discovery inspects each physical archive's own bounded manifest, ZIP entries, small Corda metadata/resources and, for older CorDapps, class headers and serialization annotations. It never executes supplied classes or visits method bodies. Modern CorDapp manifests and TVU entry names can establish identity even when later bytecode analysis fails.

Physical files are identified independently of names, including ZIP/JAR content in renamed .bin files. Runtime Application-ID/Class and own release/platform/vendor metadata are authoritative. Nested libraries stay inside the physical capsule boundary and never become extra normal-screen runtime, TVU or CorDapp candidates. Deep analysis inspects nested dependencies separately for exact compatibility evidence.

Every physical artifact has its own deep budget; nested archives share their containing physical artifact's limits. A deep limit produces partial compatibility coverage and prevents an unsupported readiness claim. It cannot erase established runtime, TVU or CorDapp identity. Discovery has independent limits: 1 GiB physical archives, 100,000 entries, 64 KiB metadata resources, 2 MiB individual legacy class headers and 64 MiB total legacy header input per artifact. Identities which exceed their own discovery limits remain unresolved.

Legacy CorDapps use Contract/UpgradedContract/ContractState/FlowLogic hierarchies, supported service resources or CordaSerializable annotation evidence. Arbitrary application namespaces work. A helper without sufficient evidence remains unclassified; placement in cordapps alone does not prove a CorDapp. Physical helper counts and internal coverage appear only in technical evidence.

Paths are confined to the explicitly supplied canonical root. Internal symlinks are deduplicated; external links are skipped and recorded. Multiple nodes, launch configs, runtime candidates and validators require selection. Noninteractive mode reports ambiguity instead of choosing. Validating and non-validating notaries are identified from configuration; no business role or TVU exemption is inferred.

PostgreSQL currentSchema and search_path retain ordered schema names, quoted identifiers and additional search schemas. Matching database.schema/JDBC/Hibernate/initialization defaults corroborate a primary schema. Additional search schemas do not conflict with that primary. Disagreeing defaults, unresolved substitutions, user-dependent search paths and unsupported expressions prevent an effective-schema claim. SQL folds unquoted identifiers; quoted names retain case. No database defaults are guessed.

The main environment screen shows one schema, or a count and established primary. All declarations and additional schemas remain in technical evidence. PostgreSQL mixed-case warnings are generic. Oracle and SQL Server vendors can be identified, but PostgreSQL-specific schema behavior is not asserted for them. No database connection, SQL query, schema change or migration is performed.

Discovery confidence and deep-analysis coverage are independent technical fields. HIGH identity with PARTIAL coverage is valid. Static evidence cannot prove reflective/dynamic linkage, actual signer continuity, TVU provenance or complete historical database coverage; the operator must validate these through the supported upgrade procedure.
