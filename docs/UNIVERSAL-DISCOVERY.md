# Universal discovery boundaries

Artifact discovery and compatibility analysis are separate phases. Discovery inspects each physical archive's own bounded manifest, ZIP entries, small Corda metadata/resources and, for older CorDapps, class headers and serialization annotations. It never executes supplied classes or visits method bodies. Modern CorDapp manifests and TVU entry names can establish identity even when later bytecode analysis fails.

Physical files are identified independently of names, including ZIP/JAR content in renamed .bin files. Runtime Application-ID/Class and own release/platform/vendor metadata are authoritative. Nested libraries stay inside the physical capsule boundary and never become extra normal-screen runtime, TVU or CorDapp candidates. Deep analysis inspects nested dependencies separately for exact compatibility evidence.

Every physical artifact has its own deep budget; nested archives share their containing physical artifact's limits. A broad runtime limit produces partial inventory coverage. Required active-CorDapp references are resolved independently; an unrelated broad limit does not prevent readiness when all required questions are answered. Incomplete source bytecode or incomplete required-symbol lookup still prevents readiness. It cannot erase established runtime, TVU or CorDapp identity. Discovery has independent limits: 1 GiB physical archives, 100,000 entries, 64 KiB metadata resources, 2 MiB individual legacy class headers and 64 MiB total legacy header input per artifact. Identities which exceed their own discovery limits remain unresolved.

Legacy CorDapps use Contract/UpgradedContract/ContractState/FlowLogic hierarchies, supported service resources or CordaSerializable annotation evidence. Arbitrary application namespaces work. A helper without sufficient evidence remains unclassified; placement in cordapps alone does not prove a CorDapp. Physical helper counts and internal coverage appear only in technical evidence.

Paths are confined to the explicitly supplied canonical root. Internal symlinks are deduplicated; external links are skipped and recorded. Multiple nodes, launch configs, equally strong noncanonical current runtimes, target runtimes and validators require selection. A strongly identified root corda.jar has active-location precedence; otherwise a sole strong current runtime is selected regardless of filename. Historical current runtimes are exported separately and excluded from deep analysis. Driver bodies are not inspected; their bounded signatures are included only when required by referenced classes (or when truncated identity prevents excluding that dependency). Noninteractive mode reports ambiguity instead of choosing. Validating and non-validating notaries are identified from configuration; no business role or TVU exemption is inferred.

PostgreSQL currentSchema and search_path retain ordered schema names, quoted identifiers and additional search schemas. Matching database.schema/JDBC/Hibernate/initialization defaults corroborate a primary schema. Additional search schemas do not conflict with that primary. Disagreeing defaults, unresolved substitutions, user-dependent search paths and unsupported expressions prevent an effective-schema claim. SQL folds unquoted identifiers; quoted names retain case. No database defaults are guessed.

The main environment screen shows one schema, or a count and established primary. All declarations and additional schemas remain in technical evidence. PostgreSQL mixed-case warnings are generic. Oracle and SQL Server vendors can be identified, but PostgreSQL-specific schema behavior is not asserted for them. No database connection, SQL query, schema change or migration is performed.

Discovery confidence and deep-analysis coverage are independent technical fields. HIGH identity with PARTIAL coverage is valid. Static evidence cannot prove reflective/dynamic linkage, actual signer continuity, TVU provenance or complete historical database coverage; the operator must validate these through the supported upgrade procedure.

## Resource and active-directory boundaries

Root archives use their own main manifest attributes, including wrapped lines. Unrelated main attributes and signed per-entry sections are discarded. Nested component names and metadata cannot replace an established root identity.

Default physical discovery visits root archives and direct files under cordapps, drivers, legacy-jars and legacy-contracts. Only canonical cordapps files form the active application set; drivers have a dependency role regardless of bundled application types. Other sibling directories and subdirectories inside cordapps are excluded. The existing explicit target-artifact overrides remain available.

The shipped launcher uses a 256 MiB heap. Budgeted scans read one class (maximum 2 MiB) at a time, retain compact member signatures and application references, and skip runtime method instructions. Nested archives spool sequentially to private temporary files, with 32 MiB entry, depth 4, count 128 and 512 MiB cumulative expanded-byte limits per physical archive. The central directory is limited to 8 MiB before ZipFile opens it. A shared 24 MiB conservative retention accounting ceiling for symbols, archive metadata, signatures and nested issues also spans an assessment's scans; each physical archive has independent class/reference/entry budgets. At most 512 compatibility findings and 1 MiB of finding evidence per comparison are retained, with explicit incomplete evidence on overflow. Individual symbol text is limited to 2048 characters; each physical archive is capped at 120,000 retained symbol records. These limits protect memory; they do not prove that all unscanned code is compatible.

Discovery keeps at most 4096 class names per artifact and 16384 per identity scanner, with an 8 MiB accounting ceiling for retained names and headers. Physical signature inventories retain at most 16 names of up to 1024 characters; overflow is reported as incomplete coverage without erasing the root identity. Strong manifest or targeted legacy identity survives name truncation; truncated class sets cannot establish exact rebuild matching. Limit evidence identifies the affected artifact, boundary and inspected entries/classes/references. No ready state is established while required compatibility questions remain unresolved. A normal process should have 512 MiB available memory and up to 128 MiB of writable private temporary storage in addition to its installed package.

## Required runtime symbols

Active current CorDapp bytecode is inspected before broad runtime signatures, with a separate retention budget. Every external reference retains its physical source CorDapp, source class and method, referenced owner/member/descriptor and invocation type. Repeated references to the same incompatible API produce one root cause with their source provenance retained.

Required owner classes are looked up independently in the selected current and target runtimes, including nested component JARs. A capsule remains one physical runtime. Lookup batches owners and required ancestors, skips unrelated class/resource bodies, and reads only signatures from required classes. It distinguishes exact compatibility, removed methods/fields, absent classes, changed descriptors, invocation/access incompatibility and incomplete lookup. A class is never called absent merely because the broad index omitted it.

Targeted lookup has its own bounds: 1 GiB physical archives, 256 MiB nested component files, 2 GiB cumulative reads, 500,000 directory entries, 256 nested components, depth 4, 4,096 requested owners, 2 MiB individual classes, 8 MiB compact signature storage and 90 seconds per runtime lookup. Nested components are spooled to private temporary files one at a time and deleted; raw bytes and ASM trees are not cached. Member hierarchy results are memoized per symbol (up to 4,096 entries) and discarded afterward; a 65,536-step per-runtime resolution bound stops pathological hierarchy work conservatively. Deeply nested large components may require more scratch space than the typical 128 MiB allowance; insufficient space returns incomplete evidence.

Per-symbol current/target proof is exported in required-symbol-resolution.json. Broad indexing limits remain separate in analysis-coverage.json. The normal evidence screen shows human API names, positive current-source attribution, and class/member outcomes. Missing-current proof, ambiguous duplicate definitions, malformed required bytecode or targeted limits remain unknown rather than confirmed removals.
