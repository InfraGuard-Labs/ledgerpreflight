# Universal discovery boundaries

LedgerPreflight assesses only the supplied node and upgrade-kit trees. Paths have no installation-prefix requirement. An explicitly supplied symlinked root authorizes its canonical destination; nested symlinks are traversed only inside that root. External links are skipped and reported. Mounted directories beneath a supplied root work normally. External dependencies must be supplied through existing explicit artifact overrides or a prepared tree; the tool does not scan adjacent server directories.

Node selection is bounded to 8 levels, 10,000 entries and 64 configuration candidates. Artifact scanning retains its independent bytecode/archive limits. Multiple nodes produce interactive selection; non-TTY mode returns UNKNOWN and asks for one --node path. Config ambiguity uses --node-conf or interactive selection. Multiple runtime/TVU candidates use --target-corda / --tvu-jar or interactive selection. Nested archive candidates require a separately prepared artifact before explicit selection.

HOCON supports bounded relative .conf includes, file includes, local substitutions and referenced environment variables. Include cycles, absolute paths, network/classpath includes and paths escaping the permitted configuration root are rejected. Includes within a selected node may reference sibling files. Credential values are not needed for analysis and are omitted from reports. Unresolved required configuration values remain UNKNOWN. Discovery does not inspect running processes, services or systemd.

Notary type and validating mode come from configuration. An unresolved notary field stays Unknown. Business roles remain Unknown: customer names and package naming alone do not establish an operational role. Runtime/TVU identification uses manifests/classes; CorDapp matching uses manifest identity, hashes or exact class sets, with ambiguity reported. Exact class-set matching is conservative when a restructured CorDapp lacks identity metadata. Legacy dependency purpose cannot reliably be inferred from arbitrary library bytes; use the existing --legacy-jars override where directory context is absent.

Schema evidence retains database.schema, JDBC currentSchema, Hibernate aliases and connectionInitSql search_path, including multiple search-path entries. Conflicting or unresolved declarations prevent an effective-schema claim. An unspecified default is not assumed to be public: server/user search_path may differ. PostgreSQL case warnings only apply to PostgreSQL. Oracle and SQL Server configuration vendors are identified, but vendor-specific database validation is not claimed. No JDBC connection, query, write or migration is performed by discovery or assessment.

CorDapp JAR counts are physical artifacts, not logical applications. Contract/workflow manifest identities, contained service providers and contract/flow inheritance establish CorDapp evidence, including old signed-manifest layouts. A helper under `cordapps/` is not automatically an application; other physical JARs are listed separately. Signature metadata does not prove signature validity or signing-key continuity.

Discovery confidence is HIGH when current/target runtime identities, matching TVU, CorDapps, database vendor and corroborated schema evidence are established. Missing core runtime identity gives UNKNOWN; incomplete supporting evidence gives MEDIUM with reasons. Business role is optional. Skipped external links do not erase known artifact identity, but remain incomplete-input findings that prevent an unsupported readiness claim. The terminal cursor is always ASCII `>`; arrow navigation and numbered plain-terminal fallback remain available.

Checks apply to observed artifacts and configuration. No business-role rules are invented. Notary classification does not itself waive required upgrade/TVU gates: the official Corda 4.11-to-4.12 guide requires transaction validation per node, and no unsupported exemption is inferred. Approved guided TVU remains a separate explicit operation on an operator-prepared isolated copy.
