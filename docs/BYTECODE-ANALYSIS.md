# Bytecode analysis

The scanner reads class files using ASM without loading application classes or deserializing application objects. It inventories classes, superclasses, interfaces, members and symbolic references. Member identity includes kind, name and exact JVM descriptor; methods with `Iterable` and `Collection` parameters do not match. Constructors are not inherited. Method and field static/instance mismatches are incompatible even when names and descriptors agree.

Compatibility analysis resolves available ancestor declarations conservatively. A missing ancestor prevents a definitive removed-member conclusion. Current node, target node and applicable external verifier are separate execution contexts. Duplicate copies across these contexts do not compete. Within one context, exact bound classpath or class-load evidence selects a winner; unknown or conflicting precedence remains unresolved. Selected runtime owners take precedence over supporting driver copies, without a package-name rule. Supporting dependencies cannot patch members into an existing runtime class. Declared API differences in `compare-runtime` are informational: a removed declaration may have moved to an ancestor, and a changed API matters only when something consumes it.

Required-symbol export records exact current/node/verifier outcomes and source sites separately. A compatible node with an incompatible verifier is a verifier-specific blocker. Current CorDapp bytecode supplies the compatibility question regardless of whether a target replacement CorDapp can be matched uniquely. Broad partial inventory does not downgrade an exact lookup that completed; unresolved required references still prevent readiness. Unresolved declared manifest dependencies prevent a missing-owner claim without invalidating an already selected owner's exact member proof.

Inherited member lookup uses the exact referenced name, descriptor and invocation type. Class methods can resolve through the superclass chain, including public static helpers behind a public facade and non-public generated layers. Constructors remain local to their referenced class. Interface lookup distinguishes inherited instance methods from non-inherited static/private methods and evaluates maximally specific defaults across the applicable hierarchy. Field resolution preserves interface-before-superclass search. Inaccessible members, invocation mismatches, conflicting defaults and unresolved required ancestors cannot establish compatibility. These rules follow [JVM member resolution](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-5.html#jvms-5.4.3) and the applicable [invocation instructions](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-6.html).

Targeted lookup discovers needed ancestors while their bounded archive is already open, then verifies newly discovered owners across the entire selected execution context before accepting a definition. Batching local ancestor discovery avoids redundant nested-archive scans; potential earlier providers are selected before their ancestor chains are expanded. Temporary signatures share the existing cache budget and are released after inspection. This is independent of broad inventory coverage and preserves archive, signature, hierarchy-work and heap limits. Exported proof retains the referenced owner, actual declaring class and declaring artifact. Compatible inherited references remain available in exports without contributing incomplete-analysis findings or obscuring a separate confirmed blocker.

References to Corda internal packages warn because ordinary stability guarantees do not cover them. A required missing internal member can block. The engine has no hardcoded list of missing members by patch release; supplied runtime bytecode determines whether a symbol exists. Synthetic tests model a class that remains present while its exact `sum(Iterable): BigDecimal` method disappears and later returns.

Class-file major versions above 61 cannot execute on Java 17. Compatible major versions alone do not prove a Java 17 rebuild, compiler version, third-party support or absence of reflective/module-access problems. Multi-release JAR selection targets Java 17, honoring the manifest's multi-release declaration. Nested runtime archives are inspected within configured archive limits.

The analyzer cannot prove reachability, reflective method names, bytecode created at runtime, every JVM resolution corner case, or contracts stored only in the ledger database. Classpath evidence and actual TVU validation remain necessary. Verification-pattern warnings identify static conversion/verify references; they do not claim a full data-flow proof. Signature block metadata is not cryptographic signer verification. Installed artifacts alone cannot establish every historical attachment or persisted constraint.

Malformed archives, path traversal, escaping symlinks, oversized entries and bounded-resource failures become coverage findings. Scanned JARs are never executed. See [Security model](SECURITY-MODEL.md) for limits and threat boundaries.


Class-only references use a separate exact-presence lookup in each execution context. They do not require member signatures, hierarchy traversal, replacement CorDapp mapping or broad index completeness. Byte-identical definitions in the same context can establish existence without inventing a winning provider; their origins remain in the export. Different definitions, unsafe required bytecode, contradictory selected-source evidence and relevant safety limits remain unresolved. This class-presence proof cannot satisfy a method or field lookup, whose exact descriptors, precedence and hierarchy rules remain unchanged.
